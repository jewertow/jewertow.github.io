Proposed — opt-in, off by default

Secretless control plane: the gateway reads its own Secrets

With pilot.secretless.enabled=true, istiod stops brokering kubernetes:// credentials. istio-agent regains a Kubernetes client, resolves them from its own namespace with the pod's projected service-account token, and serves them to Envoy over the SDS socket it already owns. The authorization decision moves out of istiod's process and into the API server's RBAC evaluation.

The credential path, step by step

  1. Envoy → istio-agent (SDS). In this mode istiod points kubernetes://my-cert at the sds-grpc UDS instead of ads {}, so the request terminates at the agent. Envoy itself is unchanged — it still only speaks SDS, and still never sees the Kubernetes API.
  2. istio-agent → API server. The agent resolves the Secret with its own Kubernetes client, using the pod's projected service-account token. Same-namespace references use a namespace-scoped watch; cross-namespace references are fetched by name, because RBAC cannot name-scope list/watch.
  3. API server decides. The read succeeds only if a Role/RoleBinding in that namespace binds gw-sa. The decision is made by Kubernetes, recorded in the audit log, and visible to any RBAC tool.
  4. istio-agent ↔ istiod (ADS). Listeners, clusters, routes — everything except credentials. istiod no longer serves Secret resources for kubernetes:// names.
  5. Envoy → istio-agent (workload identity). default / ROOTCA over the same UDS. Unchanged.
  6. istio-agent → istiod CA. CreateCertificate on 15012. Unchanged.
  7. istiod → API server. Only the Secrets it genuinely owns: CA key material, remote-cluster kubeconfigs, its own serving certificate — all in istio-system, under a namespaced Role.

Design detail to settle: step 1 assumes istiod emits sds-grpc (the agent's UDS) for kubernetes:// in this mode. The alternative — leaving ads {} in the config and having the agent's xds-proxy intercept Secret subscriptions before they reach istiod — keeps the generated config identical in both modes at the cost of a special case in the proxy. Worth naming explicitly in the RFC.

istiod RBAC in secretless mode

# ClusterRole/istiod
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "watch", "list"]
# removed entirely — cluster-wide Secret access is gone

# Role/istiod, namespace: istio-system — what istiod actually owns
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["create","get","watch","list","update","delete"]
  # CA key material, remote-cluster kubeconfigs, serving cert

Istiod's cluster-wide access to non-Secret resources is untouched. The subjectaccessreviews: create rule is no longer needed for credential brokering.

Gateway RBAC in secretless mode

# shipped with the gateway install
kind: Role
metadata: {name: gw-secret-reader, namespace: gateway-ns}
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get","list","watch"]
---
# created deliberately by the platform team, per reference
kind: Role
metadata: {name: shared-cert-reader, namespace: other-ns}
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["shared-cert"]   # name-scoped …
  verbs: ["get"]              # … so: get only, no watch

No escalation path. Istiod cannot create these bindings — Kubernetes escalation prevention forbids granting what you do not hold, and giving istiod that power would reintroduce the problem the mode solves.

Accepted limitations

  • Not Gateway API conformant in this mode. GatewayInvalidTLSConfiguration, GatewaySecretReferenceGrantSpecific and GatewaySecretReferenceGrantAllInNamespace fail: the specification models cross-namespace consent through ReferenceGrant alone, which RBAC cannot express. Default mode stays fully conformant.
  • Gateway status is not authoritative about certificate references — ResolvedRefs=Unknown. Diagnosis moves to proxy logs and metrics.
  • New obligation on platform teams: cross-namespace certificate references, and the pull secret of a root-namespace WasmPlugin that applies mesh-wide.
  • VM workloads lose credentialName — a VM has no API-server token, so Secret-backed credentials cannot be resolved there. This costs the Secret indirection, not the capability: certificates mounted on the VM's filesystem still work, so DestinationRule TLS origination keeps working through the clientCertificate / privateKey / caCertificates file paths. istio-agent serves those over SDS from disk (file-cert: / file-root:) and watches them for rotation, so Envoy picks up renewals without a restart.
  • More API-server watches — one per gateway deployment. Acceptable at the tens-of-gateways scale these deployments run at; this is why the mode is not, and is not proposed to become, the default.

Open question for maintainers

Is a documented, opt-in, explicitly non-conformant mode acceptable in upstream Istio at all — and if so, may certificate status be reported as Unknown within it?

To be resolved with Gateway API and Istio maintainers before any code. Everything else in this diagram is mechanical; this is the decision the proposal actually turns on.
