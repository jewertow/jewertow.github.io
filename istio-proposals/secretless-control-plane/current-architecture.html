istiod as credential broker

Envoy never talks to the Kubernetes API. It asks for kubernetes://my-cert over SDS, istio-agent proxies that request to istiod, and istiod serves the bytes from a cluster-wide Secret informer after deciding, in process, whether the gateway is allowed to have it — using a SubjectAccessReview.

Secretless mode →

Legend

The credential path, step by step

  1. Envoy → istio-agent. istiod generated the listener with sds_config: ads {} for kubernetes://my-cert, so the SDS request travels on Envoy's existing ADS stream to the agent's xds-proxy UDS, not on the sds-grpc socket.
  2. istio-agent → istiod. The agent does not interpret Secret resources; the xds-proxy forwards the subscription upstream over the mTLS/JWT XDS connection on port 15012.
  3. istiod → API server. SecretGen reads the Secret from a cluster-wide informer, backed by get/watch/list secrets in istiod's ClusterRole. One grant, every namespace.
  4. istiod → API server (SAR). Before serving the bytes, istiod asks the API server whether the gateway's own service account could list secrets in that namespace. The answer is advisory only — istiod already holds the Secret either way, and it is istiod that enforces the result.
  5. Envoy → istio-agent (workload identity). default and ROOTCA use the sds-grpc UDS and are served by the agent locally. Unchanged by this proposal.
  6. istio-agent → istiod CA. The agent signs a CSR via CreateCertificate on 15012 using its projected token. Not SDS, and also unchanged.

Who decides, and with what

ReferenceCheck performed by istiod
kubernetes://
Istio Gateway credentialName		 Same namespace as the proxy and a SubjectAccessReview for list secrets as system:serviceaccount:<ns>:<sa>, cached. Cross-namespace is always denied.
kubernetes-gateway://
Gateway API		 Reference must appear in VerifiedCertificateReferences — same namespace, or a ReferenceGrant. No SAR.
kubernetes-configmap://Allowed; only ca.crt is exposed.

Why this is the finding. The SAR makes istiod's decision correct, but it does not make it enforced by the API server. The only RBAC rule the cluster actually evaluates for the Secret read is istiod's own cluster-wide one. An auditor reading the RBAC graph sees a control plane that can read every Secret in the cluster; an attacker who reaches a token in istio-system inherits exactly that.

istiod RBAC today — ClusterRole

# manifests/charts/istio-control/istio-discovery/templates/clusterrole.yaml
# Needed for multicluster secret reading, possibly ingress certs in the future
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "watch", "list"]        # ← cluster-wide

- apiGroups: ["authorization.k8s.io"]
  resources: ["subjectaccessreviews"]
  verbs: ["create"]                      # ← the SAR in step 4

No namespace selector can narrow this: discoverySelectors and informer label selectors filter after the API server has authorized a cluster-wide list.

What the broker model buys

GainCost
One informer for the whole cluster — low API-server load however many gateways you run One grant with cluster-wide blast radius
Gateway pods need no Kubernetes API access at all Authorization lives in istiod's process, not in RBAC
Cross-namespace certificate references via ReferenceGrant — fully Gateway API conformant Consent is enforced by the thing that is also the broker

These are real gains, and they are why this mode stays the default. The proposal adds an alternative for operators who rank blast-radius containment above them.
